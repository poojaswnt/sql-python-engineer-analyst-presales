## 1. What Is a Database?

### The analogy

A spreadsheet stores data in rows and columns. A database takes that idea further: dozens of linked sheets, strict rules on what data is allowed, and the ability to ask complex questions across all of them simultaneously — at speed, at scale, with concurrency.

A **database** is an organised collection of structured data stored so it can be accessed, managed, and updated efficiently.

A **DBMS** (Database Management System) is the software engine — MySQL, PostgreSQL, SQLite, Oracle, SQL Server, BigQuery.

**SQL** (Structured Query Language) is the language you use to talk to any relational DBMS. One language, works everywhere (with dialect differences).

---

### Types of databases

| Type | Storage model | Examples | Best for |
|------|--------------|----------|----------|
| **Relational (RDBMS)** | Tables, rows, columns | PostgreSQL, MySQL, SQLite, SQL Server | Structured data, relationships, transactions |
| **Document** | JSON-like documents | MongoDB, Firestore, CouchDB | Flexible schema, nested/variable structures |
| **Key-Value** | Key → Value pairs | Redis, DynamoDB, Memcached | Caching, sessions, simple lookups |
| **Columnar / Analytical** | Columns not rows | BigQuery, Redshift, Snowflake, ClickHouse | OLAP, large-scale analytics, aggregations |
| **Graph** | Nodes and edges | Neo4j, Amazon Neptune | Social graphs, fraud detection, recommendations |
| **Time-Series** | Timestamped records | InfluxDB, TimescaleDB | IoT, metrics, financial ticks |
| **Search** | Inverted index | Elasticsearch, OpenSearch | Full-text search, log analysis |

> This tutorial focuses entirely on **relational** databases. As a data analyst or engineer, these will be your daily driver.

---

### OLTP vs OLAP

Two fundamentally different use cases for relational databases:

| | OLTP (Online Transaction Processing) | OLAP (Online Analytical Processing) |
|--|--------------------------------------|-------------------------------------|
| **Purpose** | Run the business | Analyse the business |
| **Operations** | Many small INSERT/UPDATE/DELETE | Few large SELECT queries |
| **Data volume** | Thousands of rows affected | Millions to billions of rows scanned |
| **Schema** | Highly normalised (3NF) | Denormalised (star/snowflake schema) |
| **Examples** | Banking app, e-commerce checkout | BI dashboards, monthly reports |
| **Tools** | MySQL, PostgreSQL | BigQuery, Redshift, Snowflake |

> You will write SQL for both. OLTP = precision. OLAP = aggregation and speed.

## 2. The Relational Model

### Core concept

Proposed by Edgar Codd at IBM in 1970. The foundation idea: **represent data as tables (relations), link them with keys, and query them with set-based operations.**

Why it dominated: predictable structure, powerful querying, ACID guarantees, and decades of tooling.

---

### Vocabulary

| Term | Plain English | Movies example |
|------|--------------|----------------|
| **Table (relation)** | Grid of data about one type of thing | `movies` table |
| **Row (record / tuple)** | One instance of that thing | One movie: *Inception* |
| **Column (attribute / field)** | One property of that thing | `title`, `year`, `rating` |
| **Primary Key (PK)** | Unique identifier per row — no duplicates, no NULLs | `movie_id` |
| **Foreign Key (FK)** | A column that references a PK in another table | `director_id` in `movies` → `directors.director_id` |
| **Schema** | The blueprint — table names, column names, types, constraints | |
| **Instance** | The actual data in the tables at a point in time | |
| **Query** | A question expressed in SQL | `SELECT title FROM movies WHERE year = 2010` |
| **Result set** | The table of rows returned by a query | |
| **Cardinality** | The number of rows in a table | `movies` has cardinality 5000 |
| **Degree** | The number of columns in a table | `movies` has degree 7 |

---

### Visual: two linked tables

```
movies                                      directors
┌──────────┬────────────────┬──────────┬─────────────────────┐   ┌─────────────┬───────────────────┬──────────────────┐
│ movie_id │ title          │ year     │ director_id (FK)    │   │ director_id │ name              │ nationality      │
├──────────┼────────────────┼──────────┼─────────────────────┤   ├─────────────┼───────────────────┼──────────────────┤
│ 1        │ Inception      │ 2010     │ 101                 │──▶│ 101         │ Christopher Nolan │ British-American │
│ 2        │ The Dark Knt   │ 2008     │ 101                 │──▶│             │                   │                  │
│ 3        │ Parasite       │ 2019     │ 102                 │──▶│ 102         │ Bong Joon-ho      │ South Korean     │
│ 4        │ Pulp Fiction   │ 1994     │ 103                 │──▶│ 103         │ Quentin Tarantino │ American         │
└──────────┴────────────────┴──────────┴─────────────────────┘   └─────────────┴───────────────────┴──────────────────┘
```

`director_id` in `movies` is a **Foreign Key**. It enforces: every movie must be linked to a real director. The link lets you answer "Who directed Inception?" without duplicating director data in every movie row.

---

### Why not one big flat table?

If you denormalised everything into one table:

```
movie_id | title      | year | director_name     | director_nationality | genre_1  | genre_2
---------|------------|------|-------------------|----------------------|----------|--------
1        | Inception  | 2010 | Christopher Nolan | British-American     | Sci-Fi   | Thriller
2        | Dark Knight| 2008 | Christopher Nolan | British-American     | Action   | Drama
```

Problems:
- **Redundancy:** "Christopher Nolan, British-American" repeated for every Nolan film
- **Update anomaly:** if his nationality is mistyped, you must fix it in 10 rows
- **Insert anomaly:** can't record a new director without also creating a fake movie
- **Delete anomaly:** delete Nolan's last movie, and you lose Nolan's record entirely
- **Multi-valued problem:** genre_1/genre_2 breaks if a film has 5 genres

The solution is **normalisation** — splitting data into focused tables and linking them with keys.

## 3. Keys, Cardinality & Relationships

### Types of keys

| Key type | Definition | Example |
|----------|-----------|---------|
| **Primary Key (PK)** | Uniquely identifies every row. NOT NULL + UNIQUE. | `movie_id` |
| **Foreign Key (FK)** | References a PK in another table. Enforces referential integrity. | `director_id` in `movies` |
| **Candidate Key** | Any column (or combo) that *could* be a PK — unique and not null | `(title, year)` could be a candidate key |
| **Composite Key** | A PK made of 2+ columns | `(movie_id, genre_id)` in `movie_genres` |
| **Surrogate Key** | An artificial PK (auto-increment integer) — not derived from real data | `movie_id = 1, 2, 3 ...` |
| **Natural Key** | A PK derived from real-world data | `isbn` for books, `passport_number` for people |
| **Super Key** | Any set of columns that uniquely identifies a row (broader than candidate key) | |
| **Unique Key** | Unique values, but NULLs allowed (unlike PK) | `email` — unique but someone might not have one |

**Surrogate vs Natural keys in practice:**

| | Surrogate (auto-increment) | Natural (real-world attribute) |
|--|---------------------------|-------------------------------|
| Stability | Always stable — never changes | Can change (names, email, codes) |
| Size | Small integer | Can be large string |
| Business meaning | None | Meaningful — human-readable |
| Recommended for | Most tables | Lookup/code tables (country codes, status codes) |

---

### Referential actions

When a referenced row (parent) is deleted or updated, what happens to the rows that point to it (children)?

```sql
CREATE TABLE movies (
    movie_id    INTEGER PRIMARY KEY,
    title       TEXT,
    director_id INTEGER REFERENCES directors(director_id)
        ON DELETE CASCADE        -- if director deleted, delete their movies too
        ON UPDATE CASCADE        -- if director_id changes, update all movies
);
```

| Action | ON DELETE | ON UPDATE |
|--------|-----------|-----------|
| `CASCADE` | Delete child rows automatically | Update child FK to new value |
| `SET NULL` | Set child FK to NULL | Set child FK to NULL |
| `SET DEFAULT` | Set child FK to its default value | Set child FK to its default value |
| `RESTRICT` | Prevent deletion if children exist | Prevent update if children exist |
| `NO ACTION` | Like RESTRICT but checked after statement | Same |

📌 **SQLite:** supports `ON DELETE CASCADE` and `ON DELETE SET NULL` but requires `PRAGMA foreign_keys = ON;` to be active — it's OFF by default.

---

### Relationship types

| Type | Meaning | Example | How to model |
|------|---------|---------|--------------|
| **One-to-One (1:1)** | Each row in A maps to exactly one row in B | Person ↔ Passport | FK in either table (add UNIQUE to make it 1:1) |
| **One-to-Many (1:N)** | One row in A maps to many rows in B | Director → Movies | FK in the "many" table (movies.director_id) |
| **Many-to-Many (M:N)** | Many rows in A map to many rows in B | Movies ↔ Genres | Junction table with two FKs |

**Junction table example (M:N):**

```
movies ──── movie_genres ──── genres
(1:N)           (FK: movie_id, FK: genre_id)        (N:1)

movie_genres
┌──────────┬──────────┐
│ movie_id │ genre_id │  ← composite PK
├──────────┼──────────┤
│ 1        │ 10       │  (Inception → Sci-Fi)
│ 1        │ 11       │  (Inception → Thriller)
│ 2        │ 12       │  (Parasite → Drama)
└──────────┴──────────┘
```

---

### Cardinality notation (crow's foot)

You'll see this in ERDs (Entity Relationship Diagrams):

```
||──────<     One to Many
||──────||    One to One
>──────<      Many to Many
o|──────<     Zero or One to Many (optional)
```

## 4. Data Integrity & Normal Forms

### The four types of data integrity

| Type | Rule | Enforced by |
|------|------|-------------|
| **Entity integrity** | Every row has a unique non-null identifier | PRIMARY KEY |
| **Referential integrity** | FK always points to a real PK value | FOREIGN KEY constraint |
| **Domain integrity** | Values are valid for their column type and range | Data type, CHECK, NOT NULL |
| **User-defined integrity** | Custom business rules | CHECK constraints, triggers, application logic |

---

### Normal Forms — what they solve

Each Normal Form adds a stricter rule. Think of them as progressive levels — passing level 3 means you also pass levels 1 and 2.

**The three anomalies normalisation prevents:**

| Anomaly | Description | Bad example |
|---------|-------------|-------------|
| **Insert anomaly** | Can't add data without inserting unrelated data | Can't record a new director unless they have a movie |
| **Update anomaly** | Changing one fact requires many row updates | Update director name → must update every movie row |
| **Delete anomaly** | Deleting one thing removes another accidentally | Delete director's last film → lose director record |

---

#### 1NF — First Normal Form

**Rules:**
1. Every cell contains one atomic (indivisible) value
2. No repeating groups of columns
3. Every row is unique (has a PK)

❌ Violates 1NF — multiple values in one cell:
```
movie_id | title      | genres
---------|------------|------------------------------
1        | Inception  | Sci-Fi, Thriller, Action    ← not atomic
```

❌ Also violates 1NF — repeating column groups:
```
movie_id | title     | genre_1 | genre_2 | genre_3
---------|-----------|---------|---------|--------
1        | Inception | Sci-Fi  | Thriller| Action
```

✅ 1NF compliant — separate junction table:
```
movies                    movie_genres
movie_id | title          movie_id | genre_id
---------|--------        ---------|----------
1        | Inception       1       | 10
                           1       | 11
                           1       | 12
```

---

#### 2NF — Second Normal Form

**Rule:** Must be 1NF + **no partial dependencies** (every non-key column must depend on the whole PK, not just part of it).
Only relevant when PK is composite.

❌ Violates 2NF — `title` depends only on `movie_id`, not on the full PK `(movie_id, genre_id)`:
```
PK: (movie_id, genre_id)
movie_id | genre_id | title       | genre_name
---------|----------|-------------|------------
1        | 10       | Inception   | Sci-Fi       ← "Inception" repeated per genre
1        | 11       | Inception   | Thriller
```

✅ Fix — split into two tables:
```
movies: (movie_id, title)
genres: (genre_id, genre_name)
movie_genres: (movie_id, genre_id)  ← junction only
```

---

#### 3NF — Third Normal Form

**Rule:** Must be 2NF + **no transitive dependencies** (non-key column A → non-key column B → PK is not allowed; A and B must both depend directly on the PK).

❌ Violates 3NF — `director_name` depends on `director_id`, which is a non-key column:
```
PK: movie_id
movie_id | title      | director_id | director_name
---------|------------|-------------|---------------
1        | Inception  | 101         | Chris Nolan
2        | Dark Knt   | 101         | Chris Nolan   ← repeated
```
Chain: `movie_id → director_id → director_name` = transitive dependency

✅ Fix — move `director_name` to a `directors` table:
```
movies:    (movie_id, title, director_id)
directors: (director_id, director_name)
```

---

#### BCNF — Boyce-Codd Normal Form

Stricter than 3NF: **every determinant must be a candidate key.**

BCNF catches edge cases where 3NF is satisfied but there are overlapping composite candidate keys. In practice: if you've achieved 3NF and have no overlapping composite candidate keys, you're also in BCNF.

**Practical guidance:** Design to 3NF/BCNF for transactional systems. Deliberately denormalise for analytics/data warehouses (star schema — see Chapter 6).

---

#### 4NF and 5NF (brief — for completeness)

| NF | Rule | When it matters |
|----|------|----------------|
| **4NF** | No multi-valued dependencies independent of each other | A movie has multiple actors AND multiple languages — store in separate tables, not one |
| **5NF** | No join dependencies that aren't implied by candidate keys | Complex decompositions — very rare in practice |

## 5. Data Types & Constraints

### Data types — full reference

**Numeric:**
| Type | Storage | Range | Use for |
|------|---------|-------|---------|
| `INTEGER` / `INT` | 4 bytes | -2B to +2B | IDs, counts, years |
| `BIGINT` | 8 bytes | -9.2 quintillion to +9.2Q | Large IDs, row counts |
| `SMALLINT` | 2 bytes | -32,768 to +32,767 | Status codes, small counters |
| `DECIMAL(p,s)` / `NUMERIC(p,s)` | Variable | Exact | Financial values — no rounding errors |
| `FLOAT` / `REAL` | 4–8 bytes | Approximate | Scientific data where precision < 100% OK |

> **Warning:** Never use FLOAT for money. `0.1 + 0.2 ≠ 0.3` in floating point. Use `DECIMAL(10,2)`.

**Text:**
| Type | Behaviour | Use for |
|------|-----------|---------|
| `TEXT` | Variable length, no limit (SQLite/PostgreSQL) | Any text — names, descriptions |
| `VARCHAR(n)` | Variable up to n characters | Names with a known max (VARCHAR(100)) |
| `CHAR(n)` | Fixed n characters, pads with spaces | Fixed codes (country codes: CHAR(2)) |

**Date/Time:**
| Type | Example | Notes |
|------|---------|-------|
| `DATE` | `2024-06-15` | Date only |
| `TIME` | `14:30:00` | Time only |
| `DATETIME` | `2024-06-15 14:30:00` | Date + time (SQLite stores as TEXT) |
| `TIMESTAMP` | `2024-06-15 14:30:00 UTC` | Date + time + timezone (PostgreSQL) |
| `INTERVAL` | `'3 days'` | Duration (PostgreSQL) |

**Other:**
| Type | Use for |
|------|---------|
| `BOOLEAN` | True/False flags (0/1 in SQLite) |
| `BLOB` | Binary data — images, files (avoid in RDBMS if possible) |
| `JSON` | JSON documents — searchable in PostgreSQL, MySQL 5.7+ |
| `UUID` | Universally unique identifiers |
| `ARRAY` | Array of values — PostgreSQL only |

📌 **SQLite** uses **dynamic typing** (type affinity) — it tries to convert values to the column's preferred type but won't reject mismatches. All other major RDBMS are strictly typed.

---

### Constraints — complete guide

```sql
CREATE TABLE movies (
    -- PRIMARY KEY: unique + not null, one per table
    movie_id    INTEGER PRIMARY KEY,

    -- NOT NULL: value must always be provided
    title       TEXT    NOT NULL,

    -- UNIQUE: all values different; NULLs are allowed (and may not be unique depending on DB)
    imdb_id     TEXT    UNIQUE,

    -- CHECK: custom validation rule
    year        INTEGER CHECK (year BETWEEN 1888 AND 2100),
    rating      REAL    CHECK (rating >= 0 AND rating <= 10),

    -- DEFAULT: value used when column omitted in INSERT
    language    TEXT    DEFAULT 'English',
    is_active   INTEGER DEFAULT 1,

    -- FOREIGN KEY with referential action
    director_id INTEGER NOT NULL
                REFERENCES directors(director_id)
                ON DELETE RESTRICT
                ON UPDATE CASCADE,

    -- GENERATED (computed) column — PostgreSQL / MySQL 5.7+ / SQLite 3.31+
    -- score_scaled REAL GENERATED ALWAYS AS (rating * 10) STORED
    created_at  TEXT    DEFAULT (DATETIME('now'))
);

-- TABLE-LEVEL constraint (needed for composite PK or composite unique)
CREATE TABLE movie_genres (
    movie_id  INTEGER REFERENCES movies(movie_id),
    genre_id  INTEGER REFERENCES genres(genre_id),

    PRIMARY KEY (movie_id, genre_id),    -- composite PK
    CONSTRAINT valid_combo UNIQUE (movie_id, genre_id)  -- named constraint
);
```

**Column-level vs Table-level constraints:**

| | Column-level | Table-level |
|--|-------------|-------------|
| Syntax | Inline with column definition | After all columns, before closing `)` |
| Required for | Single-column constraints | Composite (multi-column) constraints |
| Naming | Unnamed by default | Can be named with `CONSTRAINT name` |

**Named constraints** — always name constraints in production:
```sql
CONSTRAINT pk_movies      PRIMARY KEY (movie_id),
CONSTRAINT uq_imdb        UNIQUE (imdb_id),
CONSTRAINT fk_director    FOREIGN KEY (director_id) REFERENCES directors(director_id),
CONSTRAINT chk_year       CHECK (year BETWEEN 1888 AND 2100)
```
Named constraints give readable error messages and can be dropped by name.

## 6. Data Modelling — ERDs, Star & Snowflake Schemas

### ERD — Entity Relationship Diagram

An ERD is the blueprint of a database. Before writing a single `CREATE TABLE`, draw the ERD.

**Full movies schema ERD:**
```
directors          movies              movie_genres       genres
┌──────────────┐   ┌──────────────┐   ┌─────────────┐   ┌──────────┐
│ director_id  │◄──│ director_id  │   │ movie_id    │──▶│ genre_id │
│ name         │   │ movie_id  PK │──▶│ genre_id    │   │ genre    │
│ nationality  │   │ title        │   └─────────────┘   └──────────┘
│ birth_year   │   │ year         │
└──────────────┘   │ rating       │   movie_cast          actors
                   │ runtime_min  │   ┌─────────────┐   ┌──────────┐
                   │ box_office   │──▶│ movie_id    │   │ actor_id │
                   └──────────────┘   │ actor_id    │──▶│ name     │
                                      │ character   │   │ born     │
                                      └─────────────┘   └──────────┘
```

**ERD design steps:**
1. Identify entities (things you store data about)
2. List attributes (properties of each entity)
3. Identify relationships (how entities connect)
4. Assign cardinality (1:1, 1:N, M:N)
5. Create junction tables for M:N
6. Choose PKs (surrogate or natural)
7. Add FKs and constraints
8. Normalise to 3NF

---

### Star Schema — for analytics

OLTP databases normalise to 3NF. Analytics databases (data warehouses) use a **star schema**: one central **fact table** surrounded by **dimension tables**.

```
                    dim_date
                   ┌──────────┐
                   │ date_id  │
                   │ year     │
                   │ month    │
                   │ quarter  │
                   └─────▲────┘
                         │
dim_customer    fact_orders         dim_product
┌───────────┐  ┌────────────────┐  ┌────────────┐
│customer_id│◄─│customer_id (FK)│  │product_id  │
│name       │  │product_id  (FK)│─▶│name        │
│city       │  │date_id     (FK)│  │category    │
│segment    │  │seller_id   (FK)│  │price       │
└───────────┘  │order_id   (PK) │  └────────────┘
               │quantity        │
               │unit_price      │       dim_seller
               │discount        │      ┌──────────┐
               │revenue         │◄─────│seller_id │
               └────────────────┘      │name      │
                                       │region    │
                                       └──────────┘
```

**Fact table:** contains measurable events — each row is a transaction, click, order line. Has FKs to all dimensions, plus numeric measures (quantity, revenue, cost).

**Dimension table:** contains descriptive attributes — who, what, where, when. Denormalised on purpose for fast joins.

---

### Snowflake Schema

A snowflake schema normalises dimensions further — dimension tables link to sub-dimension tables.

```
fact_orders ── dim_product ── dim_category ── dim_department
```

| | Star Schema | Snowflake Schema |
|--|-------------|-----------------|
| Dimensions | Denormalised (flat) | Normalised (sub-tables) |
| Query speed | Faster (fewer joins) | Slower (more joins) |
| Storage | More redundancy | Less redundancy |
| Maintenance | Simpler | More complex |
| Use case | Most BI tools (Tableau, Power BI) | Very large dimensions |

> **Standard advice:** start with star schema unless your dimension tables are enormous.

---

### Slowly Changing Dimensions (SCD)

Real-world dimension data changes over time. How do you track history?

| SCD Type | Approach | Example |
|----------|---------|---------|
| **Type 0** | Never update — keep original | Customer's first registered city |
| **Type 1** | Overwrite — no history kept | Fix a typo in a name |
| **Type 2** | New row per change — full history | Customer moves city — new row with effective_from/to dates |
| **Type 3** | Add previous_value column | `current_city`, `previous_city` — one level of history |

```sql
-- SCD Type 2 example: customer address history
CREATE TABLE dim_customer (
    customer_sk     INTEGER PRIMARY KEY,   -- surrogate key
    customer_id     TEXT,                  -- natural key
    customer_city   TEXT,
    customer_state  TEXT,
    effective_from  DATE NOT NULL,
    effective_to    DATE,                  -- NULL means current record
    is_current      INTEGER DEFAULT 1      -- 1 = current, 0 = historical
);
```

## 7. CREATE, ALTER, DROP, TRUNCATE

### CREATE TABLE — full syntax

```sql
-- Complete directors table
CREATE TABLE IF NOT EXISTS directors (
    director_id   INTEGER      PRIMARY KEY,
    name          TEXT         NOT NULL,
    nationality   TEXT,
    birth_year    INTEGER      CHECK (birth_year BETWEEN 1800 AND 2010),
    bio           TEXT,
    website       TEXT         UNIQUE,
    created_at    TEXT         DEFAULT (DATETIME('now')),
    updated_at    TEXT         DEFAULT (DATETIME('now'))
);

-- Complete movies table with all constraint types
CREATE TABLE IF NOT EXISTS movies (
    movie_id      INTEGER      PRIMARY KEY,
    title         TEXT         NOT NULL,
    imdb_id       TEXT         UNIQUE,
    year          INTEGER      NOT NULL CHECK (year BETWEEN 1888 AND 2100),
    rating        REAL         CHECK (rating BETWEEN 0 AND 10),
    runtime_min   INTEGER      CHECK (runtime_min > 0),
    language      TEXT         DEFAULT 'English',
    box_office    REAL,
    is_released   INTEGER      DEFAULT 1,
    director_id   INTEGER      NOT NULL
                               REFERENCES directors(director_id)
                               ON DELETE RESTRICT
                               ON UPDATE CASCADE,
    created_at    TEXT         DEFAULT (DATETIME('now')),

    -- Table-level named constraints
    CONSTRAINT chk_movie_rating  CHECK (rating BETWEEN 0 AND 10),
    CONSTRAINT chk_runtime       CHECK (runtime_min BETWEEN 1 AND 900)
);

-- Junction table: composite PK, two FKs
CREATE TABLE IF NOT EXISTS movie_genres (
    movie_id   INTEGER  NOT NULL  REFERENCES movies(movie_id)    ON DELETE CASCADE,
    genre_id   INTEGER  NOT NULL  REFERENCES genres(genre_id)    ON DELETE CASCADE,
    PRIMARY KEY (movie_id, genre_id)
);
```

| `DELETE FROM` | All/some rows (WHERE optional) | Yes | Yes (DML) | No |


## 8. Transactions

### What is a transaction?

A transaction is a group of SQL statements treated as a **single atomic unit**. Either all succeed and are committed, or none of them take effect (rollback).

**The classic example:** bank transfer
```
Step 1: Deduct $500 from Account A  ✓
Step 2: Add $500 to Account B       ✗ (error — bank server crashed)
```
Without a transaction: money vanishes. With a transaction: Step 1 is rolled back automatically.

---

### ACID properties

| Property | Meaning | How SQL enforces it |
|----------|---------|---------------------|
| **Atomicity** | All-or-nothing — partial success impossible | ROLLBACK undoes everything on failure |
| **Consistency** | DB moves from one valid state to another valid state | Constraints checked at commit time |
| **Isolation** | Concurrent transactions don't interfere mid-execution | Locks and MVCC (Multi-Version Concurrency Control) |
| **Durability** | Once committed, changes survive crashes and restarts | Write-Ahead Logging (WAL) |

---

### Basic transaction syntax

```sql
BEGIN;                          -- or: BEGIN TRANSACTION; / START TRANSACTION;

    UPDATE directors
    SET name = 'Christopher Nolan'
    WHERE director_id = 101;

    INSERT INTO movies (title, year, director_id)
    VALUES ('Oppenheimer', 2023, 101);

    UPDATE movies
    SET rating = 8.4
    WHERE title = 'Oppenheimer';

COMMIT;                         -- make it permanent

-- If anything went wrong above:
ROLLBACK;                       -- undo everything since BEGIN
```

---

### SAVEPOINT — partial rollback

```sql
BEGIN;

    INSERT INTO movies (title, year) VALUES ('Movie A', 2024);

    SAVEPOINT sp_after_a;

    INSERT INTO movies (title, year) VALUES ('Movie B - wrong data', 2024);

    -- Movie B was wrong — roll back to savepoint only
    ROLLBACK TO SAVEPOINT sp_after_a;

    -- Movie A is still staged
    INSERT INTO movies (title, year) VALUES ('Movie B - corrected', 2024);

COMMIT;   -- saves Movie A + corrected Movie B
```

---

### Isolation levels

Isolation is about how much one transaction can see of another transaction's **uncommitted** changes.

Four standard levels (most → least strict):

| Level | Dirty Read | Non-Repeatable Read | Phantom Read | Use when |
|-------|-----------|--------------------|--------------|----|
| `READ UNCOMMITTED` | ✅ Possible | ✅ Possible | ✅ Possible | Never — data can be garbage |
| `READ COMMITTED` | ✗ Prevented | ✅ Possible | ✅ Possible | Most OLTP systems (PostgreSQL default) |
| `REPEATABLE READ` | ✗ | ✗ Prevented | ✅ Possible | Financial reports needing consistency |
| `SERIALIZABLE` | ✗ | ✗ | ✗ Prevented | Banking, inventory — full correctness |

**Phenomena explained:**
- **Dirty read:** Transaction A reads data written by Transaction B that hasn't committed yet. B rolls back → A read phantom data.
- **Non-repeatable read:** Transaction A reads a row twice; Transaction B updates it in between. A gets different values on second read.
- **Phantom read:** Transaction A queries a range twice; Transaction B inserts a new row in that range between A's reads. A's second query includes a "phantom" row.

```sql
-- Set isolation level (PostgreSQL)
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
-- ... your queries ...
COMMIT;

-- Or set for the session
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

📌 **SQLite** uses `DEFERRED`, `IMMEDIATE`, and `EXCLUSIVE` transaction modes rather than the four standard levels.

```sql
-- Update a single column
```

### UPSERT — Insert or Update

"If the row exists, update it. If it doesn't, insert it."

```sql
-- SQLite: INSERT OR REPLACE (replaces the full row)
INSERT OR REPLACE INTO movies (movie_id, title, year, rating)
VALUES (1, 'Inception', 2010, 8.9);

-- SQLite / PostgreSQL: ON CONFLICT DO UPDATE (more precise — only updates specified columns)
INSERT INTO movies (movie_id, title, year, rating)
VALUES (1, 'Inception', 2010, 8.9)
ON CONFLICT (movie_id)
DO UPDATE SET
    rating     = EXCLUDED.rating,
    updated_at = DATETIME('now');

-- ON CONFLICT DO NOTHING (silently ignore if row already exists)
INSERT INTO movies (movie_id, title, year)
VALUES (1, 'Inception', 2010)
ON CONFLICT (movie_id)
DO NOTHING;
```

📌 **MySQL uses:** `INSERT ... ON DUPLICATE KEY UPDATE`
📌 **SQL Server / Oracle use:** `MERGE INTO`

---

### MERGE — Upsert from a source table

MERGE is the SQL standard way to synchronise a target table from a source. Common in ETL pipelines.

```sql
-- PostgreSQL / SQL Server / Oracle (NOT SQLite)
MERGE INTO movies AS target
USING staging_movies AS source
    ON target.movie_id = source.movie_id
WHEN MATCHED THEN
    UPDATE SET
        title      = source.title,
        rating     = source.rating,
        updated_at = CURRENT_TIMESTAMP
WHEN NOT MATCHED THEN
    INSERT (movie_id, title, year, rating)
    VALUES (source.movie_id, source.title, source.year, source.rating)
WHEN NOT MATCHED BY SOURCE THEN
    DELETE;    -- remove rows in target that no longer exist in source
```

SQLite equivalent using three separate statements in a transaction:
```sql
BEGIN;
    -- Update existing rows
    UPDATE movies SET title = s.title, rating = s.rating
    FROM staging_movies s WHERE movies.movie_id = s.movie_id;

    -- Insert new rows
    INSERT INTO movies SELECT * FROM staging_movies
    WHERE movie_id NOT IN (SELECT movie_id FROM movies);

    -- Delete rows not in source
    DELETE FROM movies
    WHERE movie_id NOT IN (SELECT movie_id FROM staging_movies);
COMMIT;
```

## 10. SQL Execution Order

### Written order vs execution order

You write SQL in this sequence:
```
SELECT → FROM → JOIN → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT
```

But the database processes it in this order:

```
① FROM          — identify source table(s)
② JOIN          — combine tables (ON condition evaluated here)
③ WHERE         — filter individual rows (before any grouping)
④ GROUP BY      — group remaining rows into buckets
⑤ HAVING        — filter groups (after aggregation)
⑥ SELECT        — compute expressions, apply aliases
⑦ DISTINCT      — remove duplicate rows from result
⑧ ORDER BY      — sort the result set
⑨ LIMIT/OFFSET  — cut to N rows starting at offset
```

---

### Why this matters — 5 real traps

**Trap 1: Can't use SELECT alias in WHERE**
```sql
-- ❌ Fails: WHERE runs at step ③, alias defined at step ⑥
SELECT rating * 10 AS score FROM movies WHERE score > 80;
-- ERROR: column "score" does not exist

-- ✅ Fix: use the expression directly in WHERE
SELECT rating * 10 AS score FROM movies WHERE rating * 10 > 80;
-- Or use a subquery / CTE
```

**Trap 2: CAN use SELECT alias in ORDER BY and HAVING**
```sql
-- ✅ Works: ORDER BY runs at step ⑧, after SELECT
SELECT title, rating * 10 AS score FROM movies ORDER BY score DESC;

-- ✅ Works in most databases (not all): HAVING can reference aliases
SELECT director_id, COUNT(*) AS film_count
FROM movies
GROUP BY director_id
HAVING film_count > 2;  -- works in MySQL/SQLite but not PostgreSQL
-- Safe version for all databases:
HAVING COUNT(*) > 2;
```

**Trap 3: WHERE can't filter on aggregates**
```sql
-- ❌ Wrong: you can't use COUNT(*) in WHERE
SELECT director_id FROM movies WHERE COUNT(*) > 2 GROUP BY director_id;

-- ✅ Use HAVING
SELECT director_id, COUNT(*) AS cnt FROM movies GROUP BY director_id HAVING cnt > 2;
```

**Trap 4: GROUP BY must include all non-aggregated SELECT columns**
```sql
-- ❌ Wrong: title is in SELECT but not in GROUP BY or aggregate
SELECT director_id, title, COUNT(*) FROM movies GROUP BY director_id;

-- ✅ Fix
SELECT director_id, COUNT(*) FROM movies GROUP BY director_id;
-- Or if you want title: aggregate it
SELECT director_id, MIN(title) AS sample_title, COUNT(*) FROM movies GROUP BY director_id;
```

**Trap 5: DISTINCT runs after SELECT but before ORDER BY**
```sql
-- ✅ This works: ORDER BY can reference columns in SELECT even with DISTINCT
SELECT DISTINCT director_id, year FROM movies ORDER BY year DESC;

-- ❌ This fails in PostgreSQL: ORDER BY column not in SELECT with DISTINCT
-- SELECT DISTINCT title FROM movies ORDER BY year;
```

## 11. SELECT, FROM, DISTINCT, Aliases

### SELECT — full capability

```sql
-- Literal values
SELECT 'Hello' AS greeting, 42 AS answer, 3.14 AS pi;

-- All columns
SELECT * FROM movies;

-- Specific columns
SELECT title, year, rating FROM movies;

-- Arithmetic expressions
SELECT
    title,
    rating,
    rating * 10                                   AS score_100,
    ROUND(rating * 10, 1)                         AS score_rounded,
    (box_office_usd / 1000000.0)                  AS box_office_millions,
    runtime_min / 60                              AS runtime_hours,
    runtime_min - (runtime_min / 60 * 60)         AS runtime_remaining_min
FROM movies;

-- String expressions
SELECT
    title || ' (' || year || ')'          AS display_title,
    UPPER(title)                          AS title_upper,
    LOWER(title)                          AS title_lower,
    LENGTH(title)                         AS title_length,
    SUBSTR(title, 1, 10)                  AS title_short
FROM movies;

-- Conditional expressions
SELECT
    title,
    rating,
    CASE
        WHEN rating >= 9.0 THEN 'Masterpiece'
        WHEN rating >= 8.0 THEN 'Great'
        WHEN rating >= 7.0 THEN 'Good'
        WHEN rating >= 5.0 THEN 'Average'
        ELSE 'Poor'
    END AS quality_tier
FROM movies;
```

### Aliases — rules and best practices

```sql
-- Column alias with AS (recommended — explicit)
SELECT title AS movie_title, year AS release_year FROM movies;

-- Column alias without AS (works but less clear)
SELECT title movie_title, year release_year FROM movies;

-- Quoted alias — use when alias contains spaces or reserved words
SELECT title AS "Movie Title", year AS "Year Released" FROM movies;

-- Table alias — critical for readability in JOINs
SELECT m.title, m.year, d.name
FROM movies AS m
JOIN directors AS d ON m.director_id = d.director_id;

-- Self-referential alias (required for self-joins)
SELECT a.title AS film_1, b.title AS film_2
FROM movies a
JOIN movies b ON a.director_id = b.director_id AND a.movie_id < b.movie_id;
```

### DISTINCT

```sql
-- Remove duplicate rows

SELECT DISTINCT director_id, year FROM movies;

-- COUNT DISTINCT — count unique values
SELECT COUNT(DISTINCT director_id) AS directors_with_films FROM movies;
```

## 12. WHERE — Filtering

### All comparison operators

```sql
SELECT * FROM movies WHERE year = 2010;
SELECT * FROM movies WHERE year <> 2010;        -- not equal
SELECT * FROM movies WHERE year != 2010;        -- same thing
SELECT * FROM movies WHERE rating > 8.5;
SELECT * FROM movies WHERE rating >= 8.5;
SELECT * FROM movies WHERE rating < 7.0;
SELECT * FROM movies WHERE rating <= 7.0;
```

---

### BETWEEN, IN, NOT IN

```sql
-- BETWEEN is inclusive on both ends
SELECT title FROM movies WHERE year BETWEEN 2000 AND 2020;
-- Equivalent to: year >= 2000 AND year <= 2020

-- IN — value in a list
SELECT title FROM movies WHERE year IN (2008, 2010, 2019, 2023);
SELECT title FROM movies WHERE director_id IN (101, 102, 103);

-- NOT IN — watch out for NULLs!
SELECT title FROM movies WHERE director_id NOT IN (101, 102);
-- ⚠️ If the list contains a NULL, NOT IN returns no rows (NULL comparison = UNKNOWN)
-- Safe version:
SELECT title FROM movies
WHERE director_id NOT IN (SELECT director_id FROM directors WHERE nationality = 'American')
  AND director_id IS NOT NULL;
```

---

### LIKE and GLOB

```sql
-- LIKE: % matches any sequence, _ matches exactly one character
SELECT title FROM movies WHERE title LIKE 'The %';       -- starts with "The "
SELECT title FROM movies WHERE title LIKE '%Dark%';      -- contains "Dark"
SELECT title FROM movies WHERE title LIKE '%ion';        -- ends with "ion"
SELECT title FROM movies WHERE title LIKE '_nception';   -- any char + "nception"
SELECT title FROM movies WHERE title LIKE 'The __ ___'; -- "The " + 2 chars + " " + 3 chars

-- Case sensitivity: SQLite LIKE is case-insensitive for ASCII
-- PostgreSQL LIKE is case-sensitive; use ILIKE for insensitive

-- Escape a literal % or _ in a pattern
SELECT title FROM movies WHERE title LIKE '100\%' ESCAPE '\';

-- GLOB (SQLite only) — case-sensitive, Unix wildcard style
SELECT title FROM movies WHERE title GLOB 'The *';   -- * = any sequence
SELECT title FROM movies WHERE title GLOB '*[aeiou]'; -- ends in a vowel
```

---

### NULL handling — the complete guide

```sql
-- NULL is UNKNOWN — not zero, not empty string, not false
-- Any arithmetic or comparison with NULL returns NULL (except IS NULL)

SELECT * FROM movies WHERE director_id IS NULL;
SELECT * FROM movies WHERE director_id IS NOT NULL;

-- IS NOT DISTINCT FROM — treats NULL = NULL as true (PostgreSQL)
-- SELECT * FROM movies WHERE director_id IS NOT DISTINCT FROM NULL;

-- COALESCE — replace NULL with a fallback
SELECT title, COALESCE(rating, 0.0) AS rating FROM movies;
SELECT title, COALESCE(language, 'Unknown') AS language FROM movies;

-- NULLIF — return NULL when two values are equal (useful for /0)
SELECT title, NULLIF(rating, 0) AS rating FROM movies;
SELECT revenue / NULLIF(units_sold, 0) AS avg_price FROM sales;

-- IFNULL (SQLite / MySQL shorthand for COALESCE with one fallback)
SELECT title, IFNULL(rating, 0) AS rating FROM movies;
```

---

### AND, OR, NOT — precedence rules

```sql
-- AND has higher precedence than OR
-- This: a AND b OR c    is read as: (a AND b) OR c

-- Always use parentheses to be explicit:
SELECT title FROM movies
WHERE (year > 2000 OR director_id = 101)
  AND rating > 7.5;

-- NOT
SELECT title FROM movies WHERE NOT (year BETWEEN 2000 AND 2010);
SELECT title FROM movies WHERE NOT director_id IN (101, 102);

-- Complex compound conditions
SELECT title FROM movies
WHERE rating > 8.0
  AND (language = 'English' OR language = 'Korean')
  AND year >= 2010
  AND director_id IS NOT NULL;
```

---

### CASE WHEN — full syntax

```sql
-- Searched CASE (most flexible)
SELECT title,
       CASE
           WHEN rating >= 9.0                    THEN 'Masterpiece'
           WHEN rating >= 8.0 AND year > 2000    THEN 'Modern Great'
           WHEN rating >= 8.0                    THEN 'Classic Great'
           WHEN rating IS NULL                   THEN 'Unrated'
           ELSE 'Standard'
       END AS tier
FROM movies;

-- Simple CASE (like a switch — tests equality only)
SELECT title,
       CASE language
           WHEN 'English' THEN 'EN'
           WHEN 'Korean'  THEN 'KO'
           WHEN 'French'  THEN 'FR'
           ELSE 'Other'
       END AS lang_code
FROM movies;

-- CASE in WHERE — filter based on conditional logic
SELECT title FROM movies
WHERE CASE
          WHEN year > 2000 THEN rating > 8.0
          ELSE rating > 9.0     -- older films held to higher standard
      END;

-- CASE in ORDER BY — custom sort order
SELECT title, rating FROM movies
ORDER BY
    CASE WHEN rating IS NULL THEN 1 ELSE 0 END,  -- NULLs last
    rating DESC;

-- CASE in aggregate — conditional counting
SELECT
    COUNT(*)                                               AS total,
    COUNT(CASE WHEN rating >= 8 THEN 1 END)               AS high_rated,
    COUNT(CASE WHEN year > 2000 THEN 1 END)               AS modern,
    SUM(CASE WHEN language = 'Korean' THEN 1 ELSE 0 END)  AS korean_films
FROM movies;
```

```sql
SELECT m.title, d.name AS director
```

```sql
FULL OUTER JOIN directors AS d ON m.director_id = d.director_id;
-- 6 rows: all movies + all directors, NULLs where no match

-- SQLite simulation:
SELECT m.title, d.name FROM movies m LEFT  JOIN directors d ON m.director_id = d.director_id
UNION
SELECT m.title, d.name FROM directors d LEFT JOIN movies m ON d.director_id = m.director_id;
```

### CROSS JOIN

```sql
-- Every movie × every genre combination (Cartesian product)
SELECT m.title, g.genre FROM movies m CROSS JOIN genres g;
-- 5 movies × 10 genres = 50 rows

-- Implicit cross join (old SQL style — avoid in modern code)

```

### SELF JOIN

```sql
-- Movies sharing the same director
SELECT a.title AS film_1, b.title AS film_2, a.director_id
FROM movies a
JOIN movies b ON a.director_id = b.director_id
           AND a.movie_id < b.movie_id;  -- prevents (A,B) and (B,A) duplicates

-- Director pairs from same country
SELECT a.name AS director_1, b.name AS director_2, a.nationality
FROM directors a
JOIN directors b ON a.nationality = b.nationality
               AND a.director_id < b.director_id;
```

### Anti-JOIN — find rows with NO match

Anti-joins are powerful for finding "what's missing" — orphaned records, customers who never ordered, etc.

```sql
-- Method 1: LEFT JOIN + IS NULL (most readable)
SELECT d.name AS director_with_no_movies
FROM directors d
LEFT JOIN movies m ON d.director_id = m.director_id
WHERE m.movie_id IS NULL;

-- Method 2: NOT EXISTS (often fastest — stops at first match)
SELECT d.name
FROM directors d
WHERE NOT EXISTS (
    SELECT 1 FROM movies m WHERE m.director_id = d.director_id
);

-- Method 3: NOT IN (careful with NULLs!)
SELECT name FROM directors
WHERE director_id NOT IN (
    SELECT director_id FROM movies WHERE director_id IS NOT NULL  -- must exclude NULLs
);
```

---

### Non-equi JOIN — join on a condition other than equality

```sql
-- Match movies to a rating tier table (ranges)
-- rating_tiers: tier_name, min_rating, max_rating
SELECT m.title, m.rating, t.tier_name
FROM movies m
JOIN rating_tiers t ON m.rating BETWEEN t.min_rating AND t.max_rating;

-- Find all pairs of movies where one was released within 2 years of the other
SELECT a.title, b.title, ABS(a.year - b.year) AS years_apart
FROM movies a
JOIN movies b ON a.movie_id < b.movie_id
             AND ABS(a.year - b.year) <= 2;
```

---

### Multiple join conditions

```sql
-- Join on two columns
SELECT * FROM order_items oi
JOIN products p ON oi.product_id = p.product_id
               AND oi.product_version = p.version;   -- versioned product lookup

-- Join with a filter in the ON clause vs WHERE
-- These are equivalent for INNER JOIN:
SELECT m.title, d.name FROM movies m
JOIN directors d ON m.director_id = d.director_id AND d.nationality = 'American';
-- vs
SELECT m.title, d.name FROM movies m
JOIN directors d ON m.director_id = d.director_id
WHERE d.nationality = 'American';

-- But NOT equivalent for LEFT JOIN:
-- ON clause filter: left rows kept even if ON condition fails
-- WHERE clause filter: left rows with NULL match are eliminated
SELECT m.title, d.name FROM movies m
LEFT JOIN directors d ON m.director_id = d.director_id AND d.nationality = 'American';
-- ↑ All movies returned; non-American directors show as NULL
SELECT m.title, d.name FROM movies m
LEFT JOIN directors d ON m.director_id = d.director_id
WHERE d.nationality = 'American';
-- ↑ Movies with non-American directors are EXCLUDED (effectively INNER JOIN)
```

---

### 3+ table joins

```sql
-- Movie title + director name + all genres
SELECT
    m.title,
    d.name         AS director,
    GROUP_CONCAT(g.genre, ', ')  AS genres
FROM movies AS m
JOIN directors AS d       ON m.director_id = d.director_id
JOIN movie_genres AS mg   ON m.movie_id    = mg.movie_id
JOIN genres AS g          ON mg.genre_id   = g.genre_id
GROUP BY m.movie_id, m.title, d.name
ORDER BY m.title;

-- 5-table join: orders + customers + order items + products + sellers (Olist pattern)
SELECT
    o.order_id,
    c.customer_city,
    p.product_category_name,
    SUM(oi.price)              AS order_total,
    s.seller_state
FROM orders o
JOIN customers c     ON o.customer_id  = c.customer_id
JOIN order_items oi  ON o.order_id     = oi.order_id
JOIN products p      ON oi.product_id  = p.product_id
JOIN sellers s       ON oi.seller_id   = s.seller_id
WHERE o.order_status = 'delivered'
GROUP BY o.order_id, c.customer_city, p.product_category_name, s.seller_state;
```

### JOIN performance tips

```sql
-- Index the JOIN columns
CREATE INDEX idx_movies_director_id ON movies(director_id);
CREATE INDEX idx_order_items_order_id ON order_items(order_id);

-- Join smaller result sets first (hint via CTE or subquery)
```

## 14. Aggregation — GROUP BY, HAVING, GROUPING SETS

### Aggregate functions — complete reference

```sql
SELECT
    COUNT(*)                    AS total_rows,          -- counts everything including NULLs
    COUNT(director_id)          AS non_null_directors,  -- excludes NULLs
    COUNT(DISTINCT director_id) AS unique_directors,    -- distinct non-null values
    SUM(box_office_usd)         AS total_box_office,
    AVG(rating)                 AS avg_rating,
    ROUND(AVG(rating), 2)       AS avg_rating_rounded,
    MIN(year)                   AS earliest,
    MAX(year)                   AS latest,
    MAX(year) - MIN(year)       AS year_range,
    GROUP_CONCAT(title, ' | ')  AS all_titles           -- SQLite / MySQL
    -- STRING_AGG(title, ' | ') PostgreSQL
FROM movies;
```

---

### GROUP BY — rules and patterns

```sql
-- Basic grouping
SELECT director_id, COUNT(*) AS films, AVG(rating) AS avg_rating
FROM movies
GROUP BY director_id;

-- Group by multiple columns
SELECT year, language, COUNT(*) AS films
FROM movies
GROUP BY year, language
ORDER BY year, language;

-- Group by expression (not available in all databases)
SELECT
    CASE WHEN year < 2000 THEN 'Pre-2000' ELSE '2000+' END AS era,
    COUNT(*) AS films,
    AVG(rating) AS avg_rating
FROM movies
GROUP BY CASE WHEN year < 2000 THEN 'Pre-2000' ELSE '2000+' END;

-- GROUP BY with JOIN
SELECT d.name AS director, COUNT(m.movie_id) AS films,
       ROUND(AVG(m.rating), 2) AS avg_rating,
       SUM(m.box_office_usd) AS total_box_office
FROM directors d
LEFT JOIN movies m ON d.director_id = m.director_id
GROUP BY d.director_id, d.name
ORDER BY films DESC;
```

---

### HAVING — filter on aggregated results

```sql
-- Directors with more than 1 film
SELECT director_id, COUNT(*) AS films
FROM movies
GROUP BY director_id
HAVING COUNT(*) > 1;

-- Directors with avg rating > 8 AND more than 1 film
SELECT director_id, COUNT(*) AS films, AVG(rating) AS avg_r
FROM movies
GROUP BY director_id
HAVING COUNT(*) > 1 AND AVG(rating) > 8;

-- HAVING with subquery
SELECT director_id, AVG(rating) AS avg_r
FROM movies
GROUP BY director_id
HAVING AVG(rating) > (SELECT AVG(rating) FROM movies);  -- above overall average
```

**WHERE vs HAVING:**
```sql
-- WHERE: applied before grouping — filters individual rows
-- HAVING: applied after grouping — filters groups

-- Find directors of post-2000 films who have avg rating > 8
SELECT director_id, AVG(rating)
FROM movies
WHERE year > 2000               -- ← removes pre-2000 rows BEFORE grouping
GROUP BY director_id
HAVING AVG(rating) > 8;         -- ← then filters groups by avg
```

---

### GROUPING SETS, ROLLUP, CUBE — multi-level aggregation

These generate multiple GROUP BY levels in a single query. Very useful for reports.

```sql
-- GROUPING SETS: explicitly list which combinations to group by
SELECT year, language, COUNT(*) AS films
FROM movies
GROUP BY GROUPING SETS (
    (year, language),   -- subtotal by year+language
    (year),             -- subtotal by year only
    (language),         -- subtotal by language only
    ()                  -- grand total
);

-- ROLLUP: hierarchical subtotals (right to left)
SELECT year, language, COUNT(*) AS films
FROM movies
GROUP BY ROLLUP (year, language);
-- Generates: (year, language), (year), ()

-- CUBE: all combinations
SELECT year, language, COUNT(*) AS films
FROM movies
GROUP BY CUBE (year, language);
-- Generates: (year, language), (year), (language), ()

-- GROUPING() function: tells you which columns are being aggregated in that row
SELECT
    year,
    language,
    COUNT(*) AS films,
    GROUPING(year)     AS is_year_total,
    GROUPING(language) AS is_lang_total
FROM movies
GROUP BY ROLLUP (year, language);
```

📌 GROUPING SETS / ROLLUP / CUBE: supported in PostgreSQL, SQL Server, Oracle, BigQuery. **Not** in SQLite — simulate with UNION ALL.

---

### FILTER clause (PostgreSQL) — conditional aggregation cleaner syntax

```sql
-- PostgreSQL only — cleaner than CASE WHEN in aggregate
SELECT
    COUNT(*) FILTER (WHERE rating > 8)    AS high_rated,
    COUNT(*) FILTER (WHERE year > 2000)   AS modern,
    AVG(rating) FILTER (WHERE year > 2000) AS modern_avg
FROM movies;

-- Equivalent in standard SQL:
SELECT
    COUNT(CASE WHEN rating > 8   THEN 1 END) AS high_rated,
    COUNT(CASE WHEN year > 2000  THEN 1 END) AS modern,
    AVG(CASE WHEN year > 2000 THEN rating END) AS modern_avg
FROM movies;
```

## 15. ORDER BY, LIMIT, OFFSET

### ORDER BY — complete reference

```sql
-- Single column, default ASC
SELECT title, rating FROM movies ORDER BY rating;

-- DESC
SELECT title, rating FROM movies ORDER BY rating DESC;

-- Multiple columns: primary sort, then secondary
SELECT title, year, rating FROM movies
ORDER BY year DESC, rating DESC;

-- NULL positioning (NULLs go first in ASC by default in most databases)
SELECT title, rating FROM movies
ORDER BY rating ASC NULLS LAST;    -- NULLs at end (PostgreSQL syntax)
ORDER BY rating ASC NULLS FIRST;   -- NULLs at start

-- SQLite NULL positioning: in ASC, NULLs come first; in DESC, NULLs come last
-- To force NULLs last in SQLite:
SELECT title, rating FROM movies
ORDER BY CASE WHEN rating IS NULL THEN 1 ELSE 0 END, rating ASC;

-- ORDER BY position (fragile — avoid in production)
SELECT title, year, rating FROM movies ORDER BY 3 DESC;  -- 3rd column = rating

-- ORDER BY expression
SELECT title, runtime_min FROM movies
ORDER BY runtime_min / 60.0 DESC;  -- longest first

-- ORDER BY alias (works because ORDER BY runs after SELECT)
SELECT title, rating * 10 AS score FROM movies ORDER BY score DESC;
```

---

### LIMIT, OFFSET, pagination

```sql
-- Top 5 highest rated
SELECT title, rating FROM movies ORDER BY rating DESC LIMIT 5;

-- Skip first 10, return next 5 (page 3 if page_size=5)
SELECT title, rating FROM movies ORDER BY rating DESC LIMIT 5 OFFSET 10;

-- General pagination formula:
-- Page N (1-indexed): OFFSET = (N - 1) * page_size
-- Page 1: LIMIT 10 OFFSET 0
-- Page 2: LIMIT 10 OFFSET 10
-- Page 3: LIMIT 10 OFFSET 20

-- Getting total pages:
SELECT COUNT(*) FROM movies;   -- divide by page_size, round up

-- Keyset pagination (faster for large offsets — avoids scanning skipped rows)
-- Instead of: LIMIT 10 OFFSET 10000   (scans 10010 rows)
-- Use: WHERE movie_id > :last_seen_id LIMIT 10   (uses index directly)
SELECT movie_id, title, rating FROM movies
WHERE movie_id > 500      -- last movie_id from previous page
ORDER BY movie_id ASC
LIMIT 10;
```

📌 **SQL Server:** `SELECT TOP 10 ...` or `FETCH FIRST 10 ROWS ONLY`
📌 **Oracle:** `FETCH FIRST 10 ROWS ONLY` or `ROWNUM <= 10`

## 16. Subqueries

### Scalar subquery — returns one value

```sql
-- Movies rated above the overall average
SELECT title, rating
FROM movies
WHERE rating > (SELECT AVG(rating) FROM movies);

-- Most recent movie's year
SELECT title FROM movies
WHERE year = (SELECT MAX(year) FROM movies);

-- Scalar in SELECT column
SELECT title, rating,
       (SELECT AVG(rating) FROM movies) AS overall_avg,
       rating - (SELECT AVG(rating) FROM movies) AS diff_from_avg
FROM movies;
```

---

### List subquery — returns a column of values

```sql
-- Movies by directors born after 1970
SELECT title FROM movies
WHERE director_id IN (
    SELECT director_id FROM directors WHERE birth_year > 1970
);

-- Movies NOT by American directors (careful with NULLs)
SELECT title FROM movies
WHERE director_id NOT IN (
    SELECT director_id FROM directors
    WHERE nationality = 'American'
    AND director_id IS NOT NULL  -- must exclude NULLs from IN list
);
```

---

### Derived table — subquery in FROM

```sql
-- Average rating per director, filtered above 8
SELECT director_id, avg_r
FROM (
    SELECT director_id, AVG(rating) AS avg_r
    FROM movies
    GROUP BY director_id
) AS dir_stats
WHERE avg_r > 8;

-- Paginate after aggregation
SELECT *
FROM (
    SELECT director_id, COUNT(*) AS films
    FROM movies GROUP BY director_id
    ORDER BY films DESC
) AS ranked
LIMIT 5;
```

---

### Correlated subquery — references the outer query

Runs **once per row** of the outer query. Use with care on large tables.

```sql
-- Movies rated above their director's average
SELECT m.title, m.rating, m.director_id
FROM movies m
WHERE m.rating > (
    SELECT AVG(m2.rating)
    FROM movies m2
    WHERE m2.director_id = m.director_id  -- ← references outer query
);

-- Customers whose last order was above their personal average
SELECT customer_id
FROM orders o1
WHERE payment_value > (
    SELECT AVG(payment_value)
    FROM orders o2
    WHERE o2.customer_id = o1.customer_id
);
```

---

### EXISTS / NOT EXISTS

```sql
-- Directors with at least one film rated > 9
SELECT d.name
FROM directors d
WHERE EXISTS (
    SELECT 1  -- SELECT 1 is convention — EXISTS only cares if any row is returned
    FROM movies m
    WHERE m.director_id = d.director_id
    AND m.rating > 9
);

-- Directors with no films at all (anti-join via NOT EXISTS)
SELECT d.name
FROM directors d
WHERE NOT EXISTS (
    SELECT 1 FROM movies m WHERE m.director_id = d.director_id
);

-- EXISTS vs IN — when to use which:
-- EXISTS: better when the subquery is large — stops at first match
-- IN: better when the subquery returns a small list
```

---

### Subquery in SELECT — scalar per row

```sql
-- Add the director's total film count to each movie row
SELECT
    m.title,
    m.rating,
    (SELECT COUNT(*) FROM movies m2 WHERE m2.director_id = m.director_id) AS director_film_count
FROM movies m;
-- ⚠️ This is a correlated scalar subquery — runs once per row
-- Better with a window function: COUNT(*) OVER (PARTITION BY director_id)
```

---

### Subquery best practices

```sql
-- ❌ Avoid: scalar subquery in SELECT on a large table
SELECT title, (SELECT AVG(r) FROM big_table WHERE ...) FROM huge_table;
-- Runs N times for N rows — can kill performance

-- ✅ Replace with a JOIN or window function
WITH avg_cte AS (SELECT director_id, AVG(rating) AS avg_r FROM movies GROUP BY director_id)
SELECT m.title, m.rating, a.avg_r
FROM movies m JOIN avg_cte a ON m.director_id = a.director_id;
```

## 17. Set Operations — UNION, INTERSECT, EXCEPT

### Rules

- Both queries must return the same **number of columns**
- Corresponding columns must have **compatible data types**
- Column **names come from the first query**
- `UNION` / `INTERSECT` / `EXCEPT` remove duplicates; `UNION ALL` keeps them

```sql
-- UNION: all rows, duplicates removed (slower — does dedup work)
SELECT customer_id FROM orders_2022
UNION
SELECT customer_id FROM orders_2023;

-- UNION ALL: all rows, duplicates kept (faster — no dedup)
SELECT customer_id, 2022 AS yr FROM orders_2022
UNION ALL
SELECT customer_id, 2023 AS yr FROM orders_2023;

-- INTERSECT: only rows in BOTH queries
SELECT customer_id FROM orders_2022
INTERSECT
SELECT customer_id FROM orders_2023;
-- Customers who ordered in BOTH years

-- EXCEPT (MINUS in Oracle): rows in first but not second
SELECT customer_id FROM orders_2022
EXCEPT
SELECT customer_id FROM orders_2023;
-- Customers who ordered in 2022 but NOT in 2023

-- Combine with ORDER BY (applies to the full combined result)
SELECT title FROM movies WHERE year < 2000
UNION
SELECT title FROM tv_shows WHERE year < 2000
ORDER BY title ASC;
```

---

### Practical set operation patterns

```sql
-- Find products that were BOTH returned AND re-ordered (same customer)
SELECT customer_id, product_id FROM returns
INTERSECT
SELECT customer_id, product_id FROM reorders;

-- Tag each source with a label (use UNION ALL + source column)
SELECT 'Olist'    AS source, order_date, revenue FROM olist_orders
UNION ALL
SELECT 'UK Retail', invoice_date, quantity * unit_price FROM uk_retail;

-- Symmetric difference (in A or B but NOT both) — no direct SQL operator
SELECT customer_id FROM orders_2022
EXCEPT
SELECT customer_id FROM orders_2023
UNION
SELECT customer_id FROM orders_2023
EXCEPT
SELECT customer_id FROM orders_2022;
```

## 18. Window Functions — Deep Dive

### What window functions do

Window functions compute values **across a related set of rows** (the "window") without collapsing them like GROUP BY.

```
GROUP BY:  5 rows → 1 row per group (rows are merged)
WINDOW:    5 rows → still 5 rows (each row gets an extra computed column)
```

---

### The OVER() clause — anatomy

```
function_name() OVER (
    PARTITION BY col1, col2   -- defines the window/group (like GROUP BY)
    ORDER BY col3 DESC        -- defines row order within the window
    ROWS BETWEEN x AND y      -- defines the frame (subset of the window)
)
```

Each part is optional. `OVER ()` with nothing = the whole table as one window.

---

### Aggregate window functions

```sql
-- Total films per director alongside each individual film
SELECT title, director_id,
       COUNT(*)     OVER (PARTITION BY director_id) AS director_total_films,
       AVG(rating)  OVER (PARTITION BY director_id) AS director_avg_rating,
       SUM(box_office_usd) OVER ()                  AS grand_total_box_office
FROM movies;

-- Each film's % of its director's total box office
SELECT title,
       box_office_usd,
       SUM(box_office_usd) OVER (PARTITION BY director_id) AS director_total,
       ROUND(100.0 * box_office_usd /
             SUM(box_office_usd) OVER (PARTITION BY director_id), 1) AS pct_of_director
FROM movies;
```

---

### Ranking functions

| Function | Behaviour | Example output (same score tie) |
|----------|-----------|--------------------------------|
| `ROW_NUMBER()` | Unique number — ties broken arbitrarily | 1, 2, 3, 4 |
| `RANK()` | Ties share rank, next rank skips | 1, 1, 3, 4 |
| `DENSE_RANK()` | Ties share rank, no gap | 1, 1, 2, 3 |
| `NTILE(n)` | Divide into n equal buckets | bucket 1, 1, 2, 2 |
| `PERCENT_RANK()` | Relative rank 0–1 | 0.0, 0.0, 0.67, 1.0 |
| `CUME_DIST()` | Cumulative distribution 0–1 | 0.5, 0.5, 0.75, 1.0 |

```sql
-- Rank all movies by rating
SELECT title, rating,
       ROW_NUMBER() OVER (ORDER BY rating DESC) AS row_num,
       RANK()       OVER (ORDER BY rating DESC) AS rank,
       DENSE_RANK() OVER (ORDER BY rating DESC) AS dense_rank,
       NTILE(4)     OVER (ORDER BY rating DESC) AS quartile
FROM movies;

-- Top 1 per director (most common interview question)
SELECT title, rating, director_id
FROM (
    SELECT title, rating, director_id,
           ROW_NUMBER() OVER (PARTITION BY director_id ORDER BY rating DESC) AS rn
    FROM movies
)
WHERE rn = 1;

-- Top 3 per director (use rn <= 3)
SELECT * FROM (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY director_id ORDER BY rating DESC) AS rn
    FROM movies
) WHERE rn <= 3;

-- NTILE for RFM scoring
SELECT customer_id, monetary,
       NTILE(5) OVER (ORDER BY monetary ASC) AS m_score  -- 5=highest spend
FROM customer_rfm;
```

---

### LAG and LEAD — accessing other rows

```sql
-- Year-over-year comparison using LAG
SELECT year, total_revenue,
       LAG(total_revenue, 1) OVER (ORDER BY year)  AS prev_year_revenue,
       LAG(total_revenue, 2) OVER (ORDER BY year)  AS two_years_ago,
       ROUND(100.0 * (total_revenue - LAG(total_revenue, 1) OVER (ORDER BY year))
             / LAG(total_revenue, 1) OVER (ORDER BY year), 1) AS yoy_pct_change
FROM annual_revenue;

-- LAG with a default (replaces NULL for first row)
SELECT title, year, rating,
       LAG(rating, 1, 0.0) OVER (ORDER BY year) AS prev_rating  -- 0.0 if no previous row
FROM movies;

-- LEAD: look ahead to the next row
SELECT title, year,
       LEAD(title, 1) OVER (ORDER BY year) AS next_film_by_year
FROM movies;

-- Detect consecutive runs: find where a value changes
SELECT date, status,
       LAG(status) OVER (ORDER BY date) AS prev_status,
       CASE WHEN status <> LAG(status) OVER (ORDER BY date) THEN 1 ELSE 0 END AS status_changed
FROM order_status_log;
```

---

### FIRST_VALUE and LAST_VALUE

```sql
-- Best and worst film per director alongside every film
SELECT title, director_id, rating,
       FIRST_VALUE(title) OVER (PARTITION BY director_id ORDER BY rating DESC) AS best_film,
       LAST_VALUE(title)  OVER (
           PARTITION BY director_id
           ORDER BY rating DESC
           ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING  -- ← required for LAST_VALUE
       ) AS worst_film
FROM movies;
-- Without the ROWS BETWEEN clause, LAST_VALUE only sees rows up to the current row
```

---

### Frame clauses — controlling the window

```
ROWS BETWEEN x AND y    — physical rows
RANGE BETWEEN x AND y   — logical value range

x and y can be:
    UNBOUNDED PRECEDING  — first row of partition
    n PRECEDING          — n rows before current
    CURRENT ROW          — current row
    n FOLLOWING          — n rows after current
    UNBOUNDED FOLLOWING  — last row of partition
```

```sql
-- Running (cumulative) total
SUM(revenue) OVER (ORDER BY date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)

-- 7-day rolling average
AVG(revenue) OVER (ORDER BY date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)

-- Centered 7-day average (3 before, current, 3 after)
AVG(revenue) OVER (ORDER BY date ROWS BETWEEN 3 PRECEDING AND 3 FOLLOWING)

-- Suffix sum (current row to end)
SUM(revenue) OVER (ORDER BY date ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING)

-- Full example: multiple windows at once
SELECT
    date,
    daily_revenue,
    SUM(daily_revenue) OVER (ORDER BY date
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)  AS running_total,
    AVG(daily_revenue) OVER (ORDER BY date
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)          AS rolling_7d_avg,
    AVG(daily_revenue) OVER (ORDER BY date
        ROWS BETWEEN 29 PRECEDING AND CURRENT ROW)         AS rolling_30d_avg,
    MAX(daily_revenue) OVER (ORDER BY date
        ROWS BETWEEN 89 PRECEDING AND CURRENT ROW)         AS rolling_90d_max
FROM daily_sales;
```

---

### Named windows — avoid repetition

```sql
-- Define the window once, reference it multiple times
SELECT title, rating,
       AVG(rating)   OVER w AS avg_r,
       MIN(rating)   OVER w AS min_r,
       MAX(rating)   OVER w AS max_r,
       RANK()        OVER w AS rnk
FROM movies
WINDOW w AS (PARTITION BY director_id ORDER BY rating DESC);
```

📌 Named windows: supported in PostgreSQL, SQLite 3.28+. Not in SQL Server.

## 19. CTEs — Common Table Expressions

### Basic CTE

```sql
-- Without CTE — nested subquery, hard to read
SELECT director_id, avg_r
FROM (SELECT director_id, AVG(rating) AS avg_r FROM movies GROUP BY director_id) t
WHERE avg_r > 8;

-- With CTE — readable, testable in isolation
WITH director_stats AS (
    SELECT director_id, AVG(rating) AS avg_r, COUNT(*) AS films
    FROM movies
    GROUP BY director_id
)
SELECT d.name, ds.avg_r, ds.films
FROM director_stats ds
JOIN directors d ON ds.director_id = d.director_id
WHERE ds.avg_r > 8
ORDER BY ds.avg_r DESC;
```

---

### Multiple CTEs — chained

Each CTE can reference the ones defined before it.

```sql
WITH
-- Step 1: base metrics per customer
customer_orders AS (
    SELECT
        customer_id,
        COUNT(*)            AS order_count,
        SUM(payment_value)  AS lifetime_value,
        MAX(order_date)     AS last_order_date
    FROM orders
    GROUP BY customer_id
),
-- Step 2: add recency score
with_recency AS (
    SELECT *,
           JULIANDAY('now') - JULIANDAY(last_order_date) AS days_since_last
    FROM customer_orders
),
-- Step 3: segment
segmented AS (
    SELECT *,
           CASE
               WHEN days_since_last <= 30  AND order_count >= 5 THEN 'Champions'
               WHEN days_since_last <= 90  AND order_count >= 2 THEN 'Loyal'
               WHEN days_since_last > 365                       THEN 'Lost'
               ELSE 'Active'
           END AS segment
    FROM with_recency
)
-- Final: group by segment
SELECT segment, COUNT(*) AS customers, ROUND(AVG(lifetime_value), 2) AS avg_ltv
FROM segmented
GROUP BY segment;
```

---

### Recursive CTE

Recursive CTEs handle hierarchical or graph-like data.

**Structure:**
```sql
WITH RECURSIVE cte_name AS (
    -- Anchor member: the starting rows
    SELECT ... base case ...

    UNION ALL

    -- Recursive member: references cte_name itself
    SELECT ... FROM source JOIN cte_name ON ...
)
SELECT * FROM cte_name;
```

**Example 1: Number series**
```sql
WITH RECURSIVE numbers AS (
    SELECT 1 AS n
    UNION ALL
    SELECT n + 1 FROM numbers WHERE n < 10
)
SELECT n FROM numbers;
-- Returns: 1, 2, 3, ..., 10
```

**Example 2: Date series (generate every day in a range)**
```sql
WITH RECURSIVE date_series AS (
    SELECT DATE('2024-01-01') AS dt
    UNION ALL
    SELECT DATE(dt, '+1 day') FROM date_series WHERE dt < '2024-12-31'
)
SELECT dt FROM date_series;
-- Every day in 2024 — useful for filling gaps in time-series data
```

**Example 3: Org chart traversal**
```sql
-- employees: emp_id, name, manager_id (NULL for CEO)
WITH RECURSIVE org_chart AS (
    -- Anchor: top-level (CEO, no manager)
    SELECT emp_id, name, manager_id, 0 AS depth, name AS path
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- Recursive: add direct reports
    SELECT e.emp_id, e.name, e.manager_id,
           oc.depth + 1,
           oc.path || ' > ' || e.name
    FROM employees e
    JOIN org_chart oc ON e.manager_id = oc.emp_id
)
SELECT depth, path FROM org_chart ORDER BY path;
```

**Example 4: Bill of Materials (manufacturing)**
```sql
-- parts: part_id, name, parent_part_id, quantity_needed
WITH RECURSIVE bom AS (
    SELECT part_id, name, parent_part_id, quantity_needed, 0 AS level
    FROM parts
    WHERE parent_part_id IS NULL

    UNION ALL

    SELECT p.part_id, p.name, p.parent_part_id,
           p.quantity_needed * b.quantity_needed AS total_qty,  -- cascade quantities
           b.level + 1
    FROM parts p
    JOIN bom b ON p.parent_part_id = b.part_id
)
SELECT level, name, total_qty FROM bom ORDER BY level, name;
```

**Recursion depth limit:**
```sql
-- PostgreSQL: set max recursion depth to prevent infinite loops
SET max_recursive_iterations = 100;

-- Guard in the query:
WITH RECURSIVE tree AS (
    SELECT id, parent_id, 0 AS depth FROM nodes WHERE parent_id IS NULL
    UNION ALL
    SELECT n.id, n.parent_id, t.depth + 1
    FROM nodes n JOIN tree t ON n.parent_id = t.id
    WHERE t.depth < 50   -- ← safety stop
)
SELECT * FROM tree;
```

---

### CTE vs Subquery vs Temp Table

| | CTE | Subquery | Temp Table |
|--|-----|----------|------------|
| Readable | ✅ Named, step-by-step | ❌ Nested, hard to read | ✅ |
| Reusable in same query | ✅ Reference multiple times | ❌ Each subquery is separate | ✅ |
| Persists between queries | ❌ Only in one statement | ❌ | ✅ |
| Materialised | Depends on DB (usually not) | No | Yes |
| Indexed | No | No | ✅ Can add indexes |
| Recursive | ✅ | ❌ | ❌ |
| Best for | Multi-step logic, readability | Simple one-off filtering | Heavy intermediate results |

## 20. Indexes & Query Performance

### How indexes work

Without an index, a query `WHERE director_id = 101` must scan every row in the table (full table scan). With an index on `director_id`, the database uses the index to jump directly to matching rows.

The most common index type is a **B-tree** (Balanced Tree):
```
        [101]
       /     \
   [50]       [150]
  /   \       /   \
[25] [75]  [125] [175]
```
Finding `director_id = 101`: start at root → go right or left → reach in O(log n) steps.

---

### Index types

| Type | When to use | Example |
|------|------------|---------|
| **B-tree (default)** | Equality, range, ORDER BY | `WHERE year = 2020`, `BETWEEN`, `<`, `>` |
| **Hash** | Equality only (faster than B-tree for =) | Lookup tables (PostgreSQL) |
| **Full-text** | Text search | `WHERE bio LIKE '%director%'` → use FTS instead |
| **Partial** | Index only a subset of rows | Index only active records |
| **Composite** | Multi-column queries | `WHERE year = 2020 AND director_id = 101` |
| **Covering** | Index includes all needed columns | Query satisfied entirely from index |
| **Expression** | Index on a computed value | Index on `LOWER(title)` |

---

### Creating indexes

```sql
-- Basic single-column index
CREATE INDEX idx_movies_year       ON movies(year);
CREATE INDEX idx_movies_director   ON movies(director_id);
CREATE INDEX idx_movies_rating     ON movies(rating);

-- Unique index (also enforces uniqueness)
CREATE UNIQUE INDEX idx_movies_imdb ON movies(imdb_id);

-- Composite index — column order matters!
-- Best for queries that filter on year first, then director
CREATE INDEX idx_movies_year_director ON movies(year, director_id);

-- Partial index (SQLite / PostgreSQL) — index only active movies
CREATE INDEX idx_active_movies ON movies(title, rating)
WHERE is_released = 1;

-- Expression index (PostgreSQL / SQLite)
CREATE INDEX idx_movies_title_lower ON movies(LOWER(title));
-- Now: WHERE LOWER(title) = 'inception' uses the index

-- Covering index: include extra columns to avoid table lookup
-- PostgreSQL: INCLUDE clause
CREATE INDEX idx_orders_customer_inc ON orders(customer_id) INCLUDE (order_date, total);
```

---

### Composite index column order

**Rule:** Put the most selective column first. Queries must use a **left-prefix** of the composite index.

```
Index: (year, director_id, rating)

✅ Uses index: WHERE year = 2020
✅ Uses index: WHERE year = 2020 AND director_id = 101
✅ Uses index: WHERE year = 2020 AND director_id = 101 AND rating > 8
❌ Can't use index: WHERE director_id = 101           (skips year — not a left-prefix)
❌ Can't use index: WHERE rating > 8                  (skips both)
✅ Partial use:    WHERE year = 2020 AND rating > 8   (uses year portion only)
```

---

### EXPLAIN / EXPLAIN ANALYZE

```sql
-- SQLite
EXPLAIN QUERY PLAN
SELECT title FROM movies WHERE director_id = 101;
-- Output shows: SCAN TABLE movies (full scan) or SEARCH TABLE movies USING INDEX

-- PostgreSQL
EXPLAIN SELECT title FROM movies WHERE director_id = 101;
EXPLAIN ANALYZE SELECT title FROM movies WHERE director_id = 101;
-- ANALYZE actually runs the query and shows actual vs estimated costs
-- Look for: Seq Scan (bad on large tables) vs Index Scan (good)

-- Key things to look for:
-- "Seq Scan" on large table → missing index
-- High "cost=" → bottleneck → add index or rewrite query
-- "Hash Join" vs "Nested Loop" → affects performance differently by data size
-- "actual rows=" very different from "rows=" → stats are stale → run ANALYZE
```

---

### Performance anti-patterns

```sql
-- ❌ Function on indexed column breaks index
WHERE YEAR(order_date) = 2023          -- function call prevents index use
-- ✅ Rewrite as range
WHERE order_date BETWEEN '2023-01-01' AND '2023-12-31'

-- ❌ Leading wildcard in LIKE
WHERE title LIKE '%dark%'              -- can't use B-tree index (unknown prefix)
-- ✅ Use full-text search, or restructure to prefix: LIKE 'The %'

-- ❌ Implicit type conversion
WHERE customer_id = 12345              -- customer_id is TEXT, 12345 is INTEGER → no index
-- ✅ Match types
WHERE customer_id = '12345'

-- ❌ SELECT * brings all columns — more I/O
SELECT * FROM orders WHERE customer_id = 'abc';
-- ✅ Select only what you need
SELECT order_id, order_date, total FROM orders WHERE customer_id = 'abc';

-- ❌ Correlated subquery per row is N full scans
SELECT *, (SELECT AVG(rating) FROM movies m2 WHERE m2.director_id = m.director_id) FROM movies m;
-- ✅ Pre-compute with CTE or window function
SELECT *, AVG(rating) OVER (PARTITION BY director_id) AS dir_avg FROM movies;

-- ❌ Unnecessary DISTINCT — often signals a JOIN issue
SELECT DISTINCT customer_id FROM orders JOIN customers USING (customer_id);
-- If customer_id is already in orders, why join customers at all?
```

---

### Database maintenance (keep stats fresh)

```sql
-- PostgreSQL: update query planner statistics
ANALYZE movies;
ANALYZE;  -- all tables

-- PostgreSQL: reclaim space after many DELETEs/UPDATEs
VACUUM movies;
VACUUM ANALYZE movies;  -- both in one

-- SQLite: reclaim space and defragment
VACUUM;
PRAGMA optimize;  -- updates stats for the query planner
```

## 21. Views & Stored Procedures

### Views

A view is a **named saved SELECT query**. It behaves like a table but stores no data — executes on every access.

```sql
-- Create a view
CREATE VIEW v_high_rated_movies AS
SELECT m.title, m.year, m.rating, d.name AS director
FROM movies m
JOIN directors d ON m.director_id = d.director_id
WHERE m.rating > 8.0;

-- Use it
SELECT * FROM v_high_rated_movies;
SELECT * FROM v_high_rated_movies WHERE director = 'Christopher Nolan';
SELECT COUNT(*) FROM v_high_rated_movies WHERE year > 2010;

-- Create or replace (avoids drop + recreate)
CREATE OR REPLACE VIEW v_high_rated_movies AS
SELECT ... updated query ...;

-- Drop a view
DROP VIEW IF EXISTS v_high_rated_movies;

-- Nested view (view on a view) — works but can hurt performance
CREATE VIEW v_nolan_high AS
SELECT * FROM v_high_rated_movies WHERE director = 'Christopher Nolan';
```

**When to use views:**
- Simplify complex joins for end users / BI tools
- Implement row-level security (show subset of data to certain users)
- Standardise reporting queries
- Create a stable API over tables (tables can change structure, view stays consistent)

---

### Materialised Views

A materialised view stores the query result physically — much faster to read, but must be refreshed.

```sql
-- PostgreSQL
CREATE MATERIALIZED VIEW mv_director_stats AS
SELECT
    director_id,
    COUNT(*)         AS total_films,
    AVG(rating)      AS avg_rating,
    SUM(box_office_usd) AS total_box_office
FROM movies
GROUP BY director_id;

-- Query it (reads cached data — very fast)
SELECT * FROM mv_director_stats WHERE avg_rating > 8;

-- Refresh when underlying data changes
REFRESH MATERIALIZED VIEW mv_director_stats;

-- Refresh without locking reads (PostgreSQL 9.4+)
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_director_stats;
```

📌 **SQLite** does not support materialised views. Use a `CREATE TABLE AS SELECT` and rebuild manually.

---

### Stored Procedures and Functions

📌 **SQLite** does not support stored procedures or user-defined SQL functions. The following is PostgreSQL.

**Function — returns a value, usable in SELECT:**
```sql
CREATE OR REPLACE FUNCTION get_director_avg_rating(p_director_id INTEGER)
RETURNS REAL
LANGUAGE SQL
AS $$
    SELECT AVG(rating)
    FROM movies
    WHERE director_id = p_director_id;
$$;

-- Use in query
SELECT title, get_director_avg_rating(director_id) AS dir_avg FROM movies;
```

**Procedure — for side effects (INSERT/UPDATE/DELETE), has transaction control:**
```sql
CREATE OR REPLACE PROCEDURE sync_director_stats()
LANGUAGE plpgsql
AS $$
BEGIN
    DELETE FROM director_stats;

    INSERT INTO director_stats (director_id, total_films, avg_rating)
    SELECT director_id, COUNT(*), AVG(rating)
    FROM movies GROUP BY director_id;

    COMMIT;
END;
$$;

-- Call it
CALL sync_director_stats();
```

### Pattern 1: Period-over-Period Comparison

```sql
WITH monthly AS (
    SELECT
        STRFTIME('%Y', order_date) AS yr,
        STRFTIME('%m', order_date) AS mo,
        SUM(payment_value)         AS revenue,
        COUNT(DISTINCT order_id)   AS orders
    FROM orders
    GROUP BY yr, mo
)
SELECT
    curr.yr, curr.mo,
    curr.revenue          AS this_year,
    prev.revenue          AS last_year,
    curr.orders           AS orders_this_year,
    ROUND((curr.revenue - prev.revenue) / NULLIF(prev.revenue, 0) * 100, 1) AS yoy_pct_change
FROM monthly curr
LEFT JOIN monthly prev
    ON curr.mo = prev.mo
    AND CAST(curr.yr AS INT) = CAST(prev.yr AS INT) + 1
ORDER BY curr.yr, curr.mo;
```

### Pattern 2: RFM Customer Segmentation

```sql
WITH rfm_raw AS (
    SELECT customer_id,
           MAX(order_date)          AS last_order,
           COUNT(DISTINCT order_id) AS frequency,
           SUM(payment_value)       AS monetary
    FROM orders GROUP BY customer_id
),
ref AS (SELECT MAX(order_date) AS max_date FROM orders),
scored AS (
    SELECT r.*,
           CAST(JULIANDAY((SELECT max_date FROM ref)) - JULIANDAY(r.last_order) AS INT) AS recency_days,
           NTILE(5) OVER (ORDER BY JULIANDAY((SELECT max_date FROM ref)) - JULIANDAY(r.last_order)) AS r_score,
           NTILE(5) OVER (ORDER BY r.frequency)  AS f_score,
           NTILE(5) OVER (ORDER BY r.monetary)   AS m_score
    FROM rfm_raw r
)
SELECT *,
       r_score + f_score + m_score AS rfm_total,
       CASE
           WHEN r_score >= 4 AND f_score >= 4              THEN 'Champions'
           WHEN r_score >= 3 AND f_score >= 3              THEN 'Loyal Customers'
           WHEN r_score >= 4 AND f_score <= 2              THEN 'New Customers'
           WHEN r_score <= 2 AND f_score >= 3              THEN 'At Risk'
           WHEN r_score = 1 AND f_score = 1                THEN 'Lost'
           ELSE 'Potential Loyalists'
       END AS segment
FROM scored;
```

### Pattern 3: Cohort Retention

```sql
WITH cohorts AS (
    SELECT customer_id,
           DATE(MIN(order_date), 'start of month') AS cohort_month
    FROM orders GROUP BY customer_id
),
activity AS (
    SELECT o.customer_id,
           DATE(o.order_date, 'start of month') AS active_month
    FROM orders o
),
joined AS (
    SELECT c.cohort_month, a.active_month,
           CAST(ROUND((JULIANDAY(a.active_month) - JULIANDAY(c.cohort_month)) / 30) AS INT) AS month_num,
           a.customer_id
    FROM cohorts c JOIN activity a ON c.customer_id = a.customer_id
),
cohort_size AS (
    SELECT cohort_month, COUNT(DISTINCT customer_id) AS sz
    FROM joined WHERE month_num = 0 GROUP BY cohort_month
)
SELECT j.cohort_month, j.month_num,
       COUNT(DISTINCT j.customer_id) AS retained,
       cs.sz                         AS cohort_size,
       ROUND(100.0 * COUNT(DISTINCT j.customer_id) / cs.sz, 1) AS retention_pct
FROM joined j JOIN cohort_size cs ON j.cohort_month = cs.cohort_month
GROUP BY j.cohort_month, j.month_num
ORDER BY j.cohort_month, j.month_num;
```

### Pattern 4: Funnel Analysis

```sql
-- Conversion funnel: browse → cart → checkout → purchase
SELECT
    COUNT(DISTINCT session_id)                                                    AS step_1_browse,
    COUNT(DISTINCT CASE WHEN step >= 2 THEN session_id END)                      AS step_2_cart,
    COUNT(DISTINCT CASE WHEN step >= 3 THEN session_id END)                      AS step_3_checkout,
    COUNT(DISTINCT CASE WHEN step >= 4 THEN session_id END)                      AS step_4_purchase,
    ROUND(100.0 * COUNT(DISTINCT CASE WHEN step >= 2 THEN session_id END)
          / COUNT(DISTINCT session_id), 1)                                        AS cart_rate_pct,
    ROUND(100.0 * COUNT(DISTINCT CASE WHEN step >= 4 THEN session_id END)
          / COUNT(DISTINCT session_id), 1)                                        AS overall_conversion_pct
FROM (
    SELECT session_id,
           MAX(CASE WHEN event = 'purchase'    THEN 4
                    WHEN event = 'checkout'    THEN 3
                    WHEN event = 'add_to_cart' THEN 2
                    ELSE 1 END) AS step
    FROM user_events GROUP BY session_id
);
```

### Pattern 5: Running Totals and Moving Averages

```sql
WITH daily AS (
    SELECT DATE(order_date) AS dt, SUM(total) AS rev
    FROM orders GROUP BY DATE(order_date)
)
SELECT dt, rev,
       SUM(rev) OVER (ORDER BY dt ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total,
       AVG(rev) OVER (ORDER BY dt ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)         AS rolling_7d,
       AVG(rev) OVER (ORDER BY dt ROWS BETWEEN 29 PRECEDING AND CURRENT ROW)        AS rolling_30d,
       rev - LAG(rev, 7) OVER (ORDER BY dt)                                         AS wow_change
FROM daily ORDER BY dt;
```

### Pattern 8: Gaps in Sequential Data

```sql
-- Find missing order IDs (gaps in a sequence)
WITH expected AS (
    SELECT MIN(order_id) + (ROW_NUMBER() OVER (ORDER BY NULL) - 1) AS expected_id
    FROM orders
    LIMIT (SELECT MAX(order_id) - MIN(order_id) + 1 FROM orders)
)
SELECT expected_id AS missing_order_id
FROM expected
WHERE expected_id NOT IN (SELECT order_id FROM orders);

-- Find date gaps in a time series (days with no orders)
WITH RECURSIVE dates AS (
    SELECT DATE(MIN(order_date)) AS dt FROM orders
    UNION ALL
    SELECT DATE(dt, '+1 day') FROM dates WHERE dt < (SELECT MAX(order_date) FROM orders)
)
SELECT d.dt AS missing_date
FROM dates d
LEFT JOIN orders o ON DATE(o.order_date) = d.dt
WHERE o.order_id IS NULL;
```

### Pattern 9: Sessionisation (group events into sessions)

```sql
-- Group user events into sessions (30-min inactivity = new session)
WITH events_with_gap AS (
    SELECT
        user_id, event_time,
        LAG(event_time) OVER (PARTITION BY user_id ORDER BY event_time) AS prev_time,
        CASE
            WHEN JULIANDAY(event_time) - JULIANDAY(
                LAG(event_time) OVER (PARTITION BY user_id ORDER BY event_time)
            ) * 24 * 60 > 30
            THEN 1 ELSE 0
        END AS is_new_session
    FROM user_events
),
session_numbers AS (
    SELECT *,
           SUM(is_new_session) OVER (PARTITION BY user_id ORDER BY event_time) AS session_num
    FROM events_with_gap
)
SELECT user_id,
       user_id || '_' || session_num AS session_id,
       MIN(event_time) AS session_start,
       MAX(event_time) AS session_end,
       COUNT(*) AS events_in_session
FROM session_numbers
GROUP BY user_id, session_num;
```

### Pattern 11: Pareto (80/20) Analysis

```sql
-- What % of products generate 80% of revenue?
WITH product_revenue AS (
    SELECT product_id, SUM(revenue) AS rev
    FROM sales GROUP BY product_id
),
cumulative AS (
    SELECT *,
           SUM(rev) OVER (ORDER BY rev DESC) AS cumulative_rev,
           SUM(rev) OVER ()                  AS total_rev,
           ROW_NUMBER() OVER (ORDER BY rev DESC) AS product_rank
    FROM product_revenue
)
SELECT
    COUNT(*) AS products_in_80pct,
    ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM product_revenue), 1) AS pct_of_total_products
FROM cumulative
WHERE cumulative_rev / total_rev <= 0.80;
```

### Pattern 12: Market Basket Analysis (co-purchased items)

```sql
-- Find pairs of products frequently bought together
WITH order_pairs AS (
    SELECT
        a.product_id AS product_a,
        b.product_id AS product_b,
        COUNT(DISTINCT a.order_id) AS times_together
    FROM order_items a
    JOIN order_items b
        ON a.order_id = b.order_id
        AND a.product_id < b.product_id   -- avoid duplicates and self-pairs
    GROUP BY a.product_id, b.product_id
)
SELECT
    p1.product_name AS product_a,
    p2.product_name AS product_b,
    op.times_together,
    ROUND(100.0 * op.times_together / (
        SELECT COUNT(DISTINCT order_id) FROM order_items WHERE product_id = op.product_a
    ), 1) AS confidence_pct    -- % of A's orders that also contain B
FROM order_pairs op
JOIN products p1 ON op.product_a = p1.product_id
JOIN products p2 ON op.product_b = p2.product_id
WHERE op.times_together >= 10
ORDER BY op.times_together DESC
LIMIT 20;
```

### Date functions

## 24. SQL Debugging — Errors, Traps, Testing

### Most common SQL errors and fixes

| Error message | Likely cause | Fix |
|--------------|-------------|-----|
| `no such column: score` | Alias used in WHERE (runs before SELECT) | Use original expression in WHERE |
| `ambiguous column name: id` | Column exists in multiple joined tables | Prefix with table alias: `m.id` |
| `syntax error near ","` | Trailing comma in column list | Remove last comma before `FROM` |
| `no such table: movies` | Table doesn't exist or wrong schema | Check spelling; run `.tables` (SQLite) |
| `FOREIGN KEY constraint failed` | FK value not in parent table | Insert parent row first, or check the value |
| `UNIQUE constraint failed` | Duplicate value in unique column | Check for existing row; use ON CONFLICT |
| `NOT NULL constraint failed` | Inserted NULL into NOT NULL column | Provide a value or add a DEFAULT |
| `division by zero` | Dividing by a column that's 0 | Use `/ NULLIF(col, 0)` |

---

### Debugging process

**Step 1: Start simple — run the innermost query first**
```sql
-- If this fails:
SELECT title FROM movies WHERE director_id IN (
    SELECT director_id FROM directors WHERE birth_year > (SELECT AVG(birth_year) FROM directors)
);

-- Test innermost first:
SELECT AVG(birth_year) FROM directors;   -- does this work?
SELECT director_id FROM directors WHERE birth_year > 1970;  -- does this work?
-- Then add the outer layer
```

**Step 2: Add columns to understand your data mid-query**
```sql
-- Unexpected results? Add diagnostic columns
SELECT m.title,
       m.director_id,
       d.director_id AS d_director_id,   -- are these actually matching?
       d.name
FROM movies m
LEFT JOIN directors d ON m.director_id = d.director_id
WHERE d.name IS NULL;  -- why are some movies unmatched?
```

**Step 3: Isolate GROUP BY issues**
```sql
-- If you get wrong counts, test without GROUP BY first
SELECT * FROM orders WHERE customer_id = 'abc' LIMIT 10;  -- see raw data
SELECT customer_id, COUNT(*) FROM orders GROUP BY customer_id LIMIT 5;  -- then group
```

**Step 4: Test NULLs explicitly**
```sql
SELECT COUNT(*), COUNT(director_id), COUNT(*) - COUNT(director_id) AS null_count
FROM movies;
```

---

### Common logic traps

**Trap 1: COUNT(*) vs COUNT(col)**
```sql
SELECT COUNT(*), COUNT(director_id) FROM movies;
-- If any director_id is NULL, these will be different!
-- COUNT(*) = all rows; COUNT(col) = non-NULL values only
```

**Trap 2: AVG ignores NULLs — may not be what you want**
```sql
-- If 3 of 10 ratings are NULL:
AVG(rating)                        -- averages 7 non-null values
SUM(rating) / COUNT(*)             -- divides sum of 7 by 10 (includes NULLs in denominator)
-- These are DIFFERENT — choose deliberately
```

**Trap 3: NOT IN with NULLs**
```sql
-- If the subquery returns any NULLs, NOT IN returns 0 rows (always)
SELECT * FROM movies WHERE director_id NOT IN (SELECT director_id FROM directors);
-- If any director_id in directors is NULL → returns nothing
-- Fix: add WHERE director_id IS NOT NULL to the subquery
```

**Trap 4: String comparison with trailing spaces**
```sql
WHERE name = 'Nolan'    -- may fail if stored as 'Nolan   '
-- Fix:
WHERE TRIM(name) = 'Nolan'
-- Or fix the data: UPDATE directors SET name = TRIM(name);
```

**Trap 5: Date stored as string**
```sql
-- If order_date is stored as 'DD/MM/YYYY' (wrong format):
WHERE order_date > '2023-01-01'   -- string comparison — may give wrong results
-- Fix: ensure ISO 8601 format 'YYYY-MM-DD' for correct string comparison
-- Or: WHERE STRFTIME('%Y-%m-%d', order_date) > '2023-01-01'
```

### SQL testing strategy

```sql
-- 1. Verify row counts at each step
SELECT COUNT(*) FROM source_table;                  -- starting count
SELECT COUNT(*) FROM source_table WHERE ...;        -- after filter
SELECT COUNT(*) FROM source_table JOIN ...;         -- after join (did rows multiply?)

-- 2. Check for unexpected duplicates after JOIN
SELECT order_id, COUNT(*) FROM (
    SELECT o.order_id FROM orders o JOIN customers c ON o.customer_id = c.customer_id
) GROUP BY order_id HAVING COUNT(*) > 1;
-- If rows appear > 1 time, there's a 1:N in a place you thought was 1:1

-- 3. Sanity-check aggregations
SELECT SUM(revenue) FROM fact_table;                -- should match known total
SELECT MIN(date), MAX(date) FROM fact_table;        -- date range correct?
SELECT COUNT(DISTINCT customer_id) FROM fact_table; -- reasonable customer count?

-- 4. Spot-check specific known records
SELECT * FROM orders WHERE order_id = 'specific_known_order';
-- Verify the result matches what you expect from the source system
```

## Appendix B: NULL Rules — Complete Guide

| Expression | Result | Reason |
|-----------|--------|--------|
| `NULL = NULL` | UNKNOWN | NULL is not equal to anything |
| `NULL != NULL` | UNKNOWN | Same |
| `NULL = 0` | UNKNOWN | NULL is not zero |
| `NULL = ''` | UNKNOWN | NULL is not empty string |
| `NULL IS NULL` | TRUE | Only way to check for NULL |
| `NULL IS NOT NULL` | FALSE | |
| `1 + NULL` | NULL | Any arithmetic with NULL = NULL |
| `'a' \|\| NULL` | NULL | Concat with NULL = NULL (except MySQL) |
| `NULL OR TRUE` | TRUE | Special case — TRUE wins |
| `NULL AND FALSE` | FALSE | Special case — FALSE wins |
| `NULL OR FALSE` | UNKNOWN | Neither dominant value |
| `NULL AND TRUE` | UNKNOWN | Neither dominant value |
| `COUNT(*)` | Counts all rows including NULLs | |
| `COUNT(col)` | Counts only non-NULL values | |
| `SUM(col)` | Ignores NULLs | Acts as if NULL rows don't exist |
| `AVG(col)` | Ignores NULLs | Denominator = non-NULL count |
| `MIN/MAX(col)` | Ignores NULLs | |
| `WHERE col IN (1, NULL)` | Matches 1 only | NULL in list is ignored |
| `WHERE col NOT IN (1, NULL)` | No rows ever | Comparison with NULL = UNKNOWN → filter out everything |
| `ORDER BY col ASC` | NULLs sort first (most databases) | Use NULLS LAST to control |

### NULL-safe functions

```sql
COALESCE(a, b, c)      -- return first non-NULL value
NULLIF(a, b)           -- return NULL if a = b, else return a
IFNULL(a, b)           -- return b if a is NULL  (SQLite/MySQL)
IIF(condition, a, b)   -- inline if (SQLite/SQL Server)
```
